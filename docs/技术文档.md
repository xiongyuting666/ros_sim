# 技术文档（开发者视角）

> 本文档从开发者角度记录本项目的技术选型、模块实现思路、关键技术难点与取舍。

## 1. 技术选型
| 项目 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | C++11 | 课程要求；同时提供 `noexcept`、`override`、初始化列表、`std::to_string` 等必要语法 |
| 编译器 | MinGW-w64 g++ 16.2.0 | Windows 下免安装、支持 C++11 全特性 |
| 构建方式 | 单命令 g++ 编译 | 源文件数量少（4 个 .cpp），无需引入 CMake，降低评阅门槛 |
| 版本管理 | Git + GitHub | 满足"增量开发痕迹"的提交规范要求 |
| 运行平台 | Windows 控制台 | 运行前调用 `SetConsoleOutputCP(CP_UTF8)` 解决中文乱码 |

## 2. 模块划分与职责
```
Node.h           抽象基类：节点名 + init()/shutdown() 纯虚接口
  └─ Publisher        话题名 + 注册/注销 + 发布（含传感器字符串重载）
  └─ Subscriber       话题名 + 注册/注销 + 消息回调
Message.h        数据载体：内容 + 自动生成时间戳 + 只读接口
  └─ SensorMessage    温度、湿度扩展
RosCore.h/.cpp   单例调度核心：三张映射表 + 转发 + 服务分发 + 全局关闭
RosException.h   四类异常：Node / Topic / Message / Service
Log.h            分级日志单例：INFO / WARN / ERROR，控制台 + 文件双输出
Service.h        服务端 Service / 客户端 ServiceClient 及请求响应数据结构
main.cpp         11 个测试场景的编排与统一异常捕获
```

**分层思路**：数据层（Message）→ 节点层（Node/Publisher/Subscriber）→ 调度层（RosCore）→ 支撑层（Log/Exception），上层调用下层，下层不反向依赖上层，避免循环包含。

## 3. 关键实现说明

### 3.1 单例 RosCore 的线程与生命周期
构造函数私有 + 静态指针延迟创建：
```cpp
RosCore* RosCore::getInstance()
{
    if(instance==nullptr) instance=new RosCore();
    return instance;
}
```
选择"静态指针 + 懒加载"而非函数内静态对象，是为了与头文件声明的 `static RosCore* instance` 形式保持一致；代价是程序结束时不会自动析构（演示程序中可接受）。

### 3.2 消息传递的浅拷贝问题
`RosCore::publish(std::string topic, Message msg)` 采用**按值传递**，简化实现、避免悬垂引用。
代价是传入 `SensorMessage` 时会发生**对象切片**，派生类的温度、湿度字段丢失。
解决办法：`SensorMessage` 的构造函数在调用父类构造时，就把温度、湿度格式化成字符串写入 `Message::data`：
```cpp
SensorMessage(double temp, double hum)
    : Message(buildSensorText(temp, hum)), temperature(temp), humidity(hum) {}
```
这样即使发生切片，订阅端仍能从 `getData()` 拿到完整传感器信息。这是在"不引入多态指针传递"前提下最省事的做法。

### 3.3 注销节点时的迭代器失效
从 `std::vector` 中删除元素必须使用 `erase` 的返回值续接迭代器，否则 `++iter` 跳过元素甚至越界：
```cpp
for(auto iter=vec.begin(); iter!=vec.end();)
{
    if(*iter==sub) iter=vec.erase(iter);
    else ++iter;
}
```

### 3.4 全局关闭时的"边遍历边修改"
`shutdownAll()` 中若直接遍历 `subMap`，而 `sub->shutdown()` 内部又会调用 `unregSubscriber` 修改同一个容器，会造成迭代器失效。
解决：先拷贝快照再遍历。
```cpp
std::map<std::string, std::vector<Subscriber*>> subSnapshot = subMap;
for(auto& entry : subSnapshot) { ... }
```
这是本项目最容易踩、也最隐蔽的一个坑。

### 3.5 异常分级与"程序不崩溃"
四类异常均继承 `std::exception` 并重写 `what()`，携带中文语义信息。
`main.cpp` 用模板函数 `runCase()` 把每个场景包在独立的 try-catch 中，catch 顺序按派生关系排列，每个 catch 只做日志输出、不重新抛出，从而保证单个场景失败不影响后续场景——这正是需求中"程序禁止崩溃"的落地方式。

### 3.6 日志设计
`Log` 为单例，`std::ofstream` 以追加模式打开 `log.txt`，一次日志同时写控制台与文件，格式统一为：
```
[时间] [等级] 内容
```
`ctime()` 返回值末尾带换行符，需 `pop_back()` 去掉，否则日志会断行。
已知局限：`ctime` 非线程安全，多线程场景需换 `std::localtime_r` 或加锁。

### 3.7 服务通信模型
- 服务端 `Service` 持有函数指针 `Handler`，注册进 `RosCore::serviceMap`（服务名唯一）。
- 客户端 `ServiceClient::call()` 通过 RosCore 查表转发，**同步阻塞**取得 `ServiceResponse` 后才继续执行，与发布订阅的"不等响应"形成对照。
- 为避免头文件循环包含（RosCore.h 需要 Service.h，Service.h 又需要 RosCore），把 `ServiceClient::call` 的实现放到 `RosCore.cpp` 中。

## 4. 已知问题与改进方向
| 问题 | 现状 | 改进方案 |
| --- | --- | --- |
| 单例未释放 | `new` 后无 `delete` | 改为函数内静态对象，或使用 `std::unique_ptr` |
| 消息切片 | 按值传递导致派生类字段丢失 | 改为 `std::shared_ptr<Message>` 或 `Message&` + 基类虚接口 |
| 日志非线程安全 | `ctime` 不可重入 | 加 `std::mutex`，改用可重入时间函数 |
| 节点对象生命周期 | 演示中用 `new` 且未 `delete` | 引入 `std::unique_ptr` 或统一由 RosCore 托管 |
| 异步真实性 | 回调同步执行 | 引入消息队列 + 工作线程真正异步派发 |
